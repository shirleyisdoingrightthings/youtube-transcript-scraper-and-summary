# 面向读者的精编稿二次复核规范（Reader-Facing Review）

> **调用方式**：当用户把一段（或几段）已成形的逐字稿 / 精编稿发来，要求"复核""二次复核""帮我看看这段有没有问题""对照字幕检查"时，加载并执行本规范。
> **定位**：本规范处理的是**面向读者发布的精编稿**（公众号 / Blog），**不是严格逐字稿**——因此"为读者落地而做的增补"是加分项，而非违规。
> **配套**：生成阶段用 `dialogue_transcript.md` / `illustrated_deepdive.md`；术语统一始终查 `glossary.md`；本规范用于生成之后的逐段打磨。

---

## 执行顺序（固定四步 + 产出）

每次复核按 A→B→C→D 跑一遍，最后给"完整优化版"。**先报问题、再改稿**，不要把问题藏在改稿里让用户自己找。

### A. 对照字幕核校（忠实度 + 语言表述）

1. 打开该段对应的 `transcript.json`（原始字幕），逐句比对译文。
2. **区分三档，分别处理**：
   - 🔴 **必改硬伤**：事实/数字/专名错误、逻辑反转、**意思译反或译丢**（典型：把 "have conversations with folks I support" 误成"安排会议"；catch a bug 误成"引出新 bug"）。逐处列出"原文→你的稿→正确译法"。
   - 🟡 **轻微偏差**：语义略漂、漏掉招牌词/关键限定（如 trust but verify、high accountability）。给出建议但标为可选。
   - 🔵 **可选润色**：语序、节奏、措辞，由用户定。
3. **专名核对铁律**：外文公司/产品/模型/人名，先查证官方写法（WebSearch/WebFetch 或用户随稿提供的参考清单），查不到就标 `⚠️建议人工核对`，绝不照搬音译猜测。
4. **每段给总判定**：`✅ 本段无硬伤` 或 `⚠️ 本段 N 处硬伤`，不让用户猜。

### B. 标题诊断（标题准不准 + 标题与内容是否对应 + 分段是否合理）

1. **标题要具体**：禁用功能性/描述性标题（❌"工程师角色的转变""关于 X 的讨论"）。标题要短，但必须点出这节到底讲什么，最好直接是一句有判断力的钩子。
2. **标题↔内容必须对应**：核对每节标题下的内容是否真的在讲这个标题。**对照字幕时间线检查标题是否"挂错了内容"或"整体错位一位"**（高频错误：复制粘贴时标题与内容错位）。发现错位，明确指出并重新对齐。
3. **分段是否合理**：一节只讲一个主题。若一节里塞了两拍（如"管理者掌握全局"+"验证成新瓶颈"），建议**拆成两节**或补一句显式过渡。相邻同主题碎节则建议**合并**。精编稿一篇约 8 节为宜。
4. 给出"建议标题对照表"（你的标题 → 实际内容 → 建议标题）。

### C. 面向读者的增补（帮非技术 / 非 Claude Code 用户落地）

1. **这是精编稿、不是严格逐字稿**，可以为读者补充背景，让内容更易懂。增补的两类对象：
   - 不熟悉 Claude Code / Cowork 的读者：解释功能是什么、解决什么问题。
   - 非技术读者：解释 repo、PR、TDD、Spec、cron job、分布式系统、async 等术语。
2. **增补必须与嘉宾原话明确区分**：统一用灰框（`> 🔍 名词解释 · …`）或显式"编者注"，绝不混入说话人发言冒充原话。
3. **Claude Code / Cowork 功能解释必须准确**（常备口径，拿不准先查证再写）：
   - **Routines**：定时自动化，但比 cron job 多一层——会 prompt agent、直接生成 PR 供审、发现 bug 可直接修。"到点派一个会思考的助手把活办完"，而非"到点跑一条死命令"。
   - **Skills**：把一套标准/做法打包成可复用指令，放进仓库供 Claude 反复调用。
   - **Spec**：规范文档，"什么算对/好"的书面标准；check 进仓库与代码一起更新。
   - **Code Review（自动代码评审）**：合并前让 Claude 对照规则挑问题、给建议。
   - **常驻远程会话**：长期挂云端、能读所有 repo/Slack/指标的 Claude 实例，相当于管理者的"全局仪表盘"。
   - **PR / repo / dogfooding / agent 舰队 / async / latent demand / agency**：按 glossary 与通用口径简释。
4. **增补是加分不是改原意**：只补背景、不替嘉宾下新结论；补充的事实若无出处，标 `⚠️建议人工核对`。

### D. 篇幅与取舍（嘉宾画像决定详略）

1. **结合嘉宾身份判断详略**：资深高管 / 一线负责人，读者更想看**结合应用的实例、方法论、技术判断**，而非大段个人前史。
2. **倾向保留**：关键技术判断、产品/管理实例、可独立引用的金句、可复制的方法论、数据。
3. **倾向压缩或删除**：冗长的个人成长背景故事、纯铺垫长问、重复论证、绕回去又说一遍的内容、广告口播。
4. 删除某节时，检查**它是否是后文的铺垫**；若是，把后文里依赖它的那句改写成不依赖前文的版本，保证衔接不断。

## 产出格式

1. **核校与诊断报告**（先给）：A 的硬伤清单（🔴/🟡/🔵）+ 总判定；B 的标题诊断表；C 的增补建议；D 的取舍建议。最关键的问题放最前。
2. **完整优化版**（后给）：按上述建议改好的整段，含增补灰框、对齐后的标题、修正后的译文。
3. **去 AI 味自检**：定稿前扫一遍——少用破折号、慎用"不是…而是…"、删包装词与空转连接（详见 `dialogue_transcript.md` 去 AI 味章节）。
4. 若涉及永久性规范变更，按 CLAUDE.md Step 6 Meta-Harness 提示用户确认后再落文档。

## Agent Council 三角色协议（两个关口共用）

本工作流在两处用 **Agent Council** 做互审（详见 CLAUDE.md 的 Step 2.6 交付前自检、Step 4.5 定稿前终审）。

> **沿革**：本协议原为"评审 Agent → 核实 Agent → 主模型协调"两角色机制，2026-09-10 改为下述三角色机制——把"协调"从主模型移交给独立的 Judge Agent，原因是主模型综合双方意见时天然偏向自己写的初稿，等于自己裁自己；实测三角色能纠正这个偏差（曾纠正过一次误判为"零必改"的复核结论，并追加发现了主模型自己漏掉的几处硬伤）。

**机制（三角色，两轮）：**

1. **第一轮 · 两位审稿人并行、互不知情**：
   - **激进审稿人**（progressive）：按 `skills/council/progressive.md` 执行，倾向多报。
   - **保守审稿人**（conservative）：按 `skills/council/conservative.md` 执行，倾向少报但守住忠实度与讲者原声，专门反向检查"有没有被过度纠正"。
   - 两者都是**全新 Agent**，各自独立完整读一遍成品与字幕，互不可见对方的产出。
2. **第二轮 · Judge 裁决**：按 `skills/council/judge.md` 执行，读两份审稿报告（必要时读主模型准备的证据卷宗），逐条裁定成立/不成立，冲突处明确站边，产出可直接执行的「把 X 改成 Y」清单。
3. **主模型执行裁决**：按 Judge 给出的必改清单逐条落地，每条改动前先确认「X 在稿中唯一」再替换（避免误改重名片段），执行完跑一遍 `check_transcript_edit.py`，再向用户汇报"可发布"判定与分数。
4. **轮数上限（强制 · 防止无限循环）**：「审稿 → 裁决 → 落地」整套算一轮（上文"两轮"指一轮内部的两个步骤，不是这里的轮数）。落地后若改动涉及正文事实或结构、需要再审，最多再跑到**第 3 轮**。退出条件二选一：① Judge 判定**必改清零** → 报"可发布"；② 第 3 轮结束仍有必改 → **停下，不再起第 4 轮**，用下表向用户汇报，由用户拍板是手动处理、放宽标准还是再加一轮。

   | 项 | 值 |
   |---|---|
   | 已跑轮数 | N / 3 |
   | 已清必改 | N 处 |
   | 剩余必改 | N 处（逐条列出：位置 + Judge 原话） |
   | 反复出现的项 | 连续两轮都被判必改、改了又回来的条目（通常说明两位审稿人标准冲突，需要人定） |

**模型分配（用 `Agent` 工具时通过 `model` 参数指定；不支持按角色选模型的环境下按下方"环境限制"处理）：**

| 角色 | 建议档位 | 理由 |
|---|---|---|
| 激进 / 保守审稿人 | 中间档（如 `model: "sonnet"`） | 任务是逐句比对原文列问题，不需要最强档；两人独立跑，用中间档能把这一环的成本压低，多轮迭代也负担得起 |
| Judge | 最强档（如 `model: "opus"`） | 唯一要仲裁两份对立意见、必要时否决审稿人判断的角色，且其裁决直接决定改什么，值得用最强档 |

- **环境限制**：若当前工具不支持按 Agent 指定模型（三个角色都会继承主会话的模型），跳过上表，三角色仍按本协议的读写与裁决流程走，只是不做差异化分配。
- **模型必须显式指定，不要假设默认值可用。** 起 Agent 前若不确定某个模型名在当前环境是否可用，先用一次简单调用探测；遇到 `model_not_found` / 404 一类错误，**如实告诉用户这是当前环境的模型别名或路由配置问题**，不要反复重试同一个模型名，也不要静默换成别的模型继续跑（换模型档位是本协议允许的降级选项之一，但要在汇报里说清楚换了什么、为什么）。

**两条铁律（对三个角色都成立）：**
- **必须是全新 Agent**——模型不能给自己打分，也不能给自己裁决（生成稿的会话不得身兼审稿人或 Judge）。
- **必须喂完整正文，绝不喂压缩摘要**——实测教训：曾因把正文压成"分号串要点"喂给评审 Agent，导致它误判"分号流水账 / 可读性崩塌"，靠第二个 Agent 拿真稿才纠偏。压缩稿会制造假阳性。**Judge 例外**：Judge 不通读正文与字幕全文，而是按审稿报告给的定位做定点抽取（见 `skills/council/judge.md` 第一节）——这是为了控制阅读量，不是走"喂摘要"的老路，两者的区别是 Judge 仍然要对每条裁决回原文验证，只是不做无目的的通读。

**产出必须当场落盘（强制）**：两位审稿人与 Judge 各自的报告，必须在该 Agent **结束前**写入 `output/<标题>/` 目录（文件名见各角色模板），不能只留在对话回复或会话临时目录里。**实例教训**：曾有一轮审稿的完整报告只存在于上一个会话的临时目录，换一个会话/换一个工具接手时找不到，被误记为"未交卷"，直到几天后才在临时目录里翻出来。落盘的文件同时也是「归档三件套」之外的审计记录，允许长期保留在该稿目录下。

**某个角色中途失败时的处理**：

- **审稿人（激进/保守）失败**：直接重跑同一角色即可，不影响另一位。若连续失败，先确认是不是模型/额度问题（见上「模型分配」的探测建议），如实告诉用户，不要在未说明的情况下悄悄换成主模型代答。
- **Judge 失败**：**不允许由主模型代行**——Judge 存在的意义就是不让生成稿的那一方自己拍板，主模型代行会让这道关口形同虚设。失败后重跑 Judge（必要时换成更省 token 的读法，如先由主模型补一份 `_council_evidence_dossier.md` 把已核实的外部事实喂给它，减少它自己查证的开销），或明确告知用户"这一步反复失败，需要你决定是重试还是先按审稿人的共识手动清理"。
- **两次记录到这个坑**：`~/.claude/settings.json` 的模型映射配置若被改成指向不存在的模型（例如切换过第三方 API 供应商后忘记改回来），子 Agent 会成批 404、Judge 反复失败。这类问题**报出真实错误原因**即可，不属于本协议要处理的范围，但发现时应提示用户去检查会话的模型配置。

**读回线上稿**：若稿子已在 Notion，用 `python3 notion_read.py <page_id_or_url>` 把完整正文读回本地再喂给 Council。注意：页面被移出上传数据库后集成会返回 404，需在 Notion 把该页重新「连接（Connections）」给集成 `claude code youtube transcript scraper and summary` 才能读写。

## 模式 A（图文精读）专用复核清单

上面 A→D 四步对两种模式通用（对照字幕、标题诊断、增补、篇幅取舍）。**复核图文精读稿（或 Agent Council 评审图文精读）时，评审维度在 A–D 之外，额外按 9 段式结构再查一遍：**

- [ ] **9 段式完整**：标题 / 摘要钩子 / 封面 Prompt / 内容与价值概括 / 嘉宾背景 / 核心观点 / 重构正文 / 收束段 / 系列回链——**双锚点（价值概括 + 收束段）都在、不可缺**。
- [ ] **价值概括 ↔ 嘉宾背景 零重复**：人物履历只在嘉宾背景出现，价值概括只讲事。
- [ ] **路线条**：价值概括末尾有 `📍 本文路线` 导航，关键词与正文大标题一一对应，末项用中性词（不预设输赢）。
- [ ] **减负装置**（6000 字以上必查）：路线图句（开头）+ 一句话路标（中途 2-3 处）+ "说人话"保底句（硬核段）是否到位。
- [ ] **章节标题叙事化、且与正文精确对应**（无"挂羊头卖狗肉"、无功能性标题）。
- [ ] **核心观点成逻辑链**（判断→旧路不行→新路跑通→真正方案→结论），而非并列罗列；标题是钩子句、无编号、无 `概念名：描述` 拼接。
- [ ] **媒体占位**：🖼️/🎞️ 嵌在对应段落、8–15 个不泛滥。
- [ ] **收束段**：给"两面"判断 + 留开放结局，落在事实上、不预设输赢。
- [ ] 去 AI 味、对照 `glossary.md` 术语统一。

> Agent Council 的两位审稿人按模式切换打分维度：逐字稿用 A–D；图文精读用 A–D + 本清单。
