# 对话体逐字稿生成规范

当用户要求生成"对话体逐字稿"（而非图文精读稿）时，必须严格遵守以下原则与结构。

## 核心定位

逐字稿的价值在于**还原对话现场**，让读者能像"旁听者"一样自行提炼观点。但单纯的逐字稿过于冗长难读，必须在前面加一层结构化的导读层（开篇金句 + 导语 + 嘉宾背景 + 核心观点），帮助读者在投入完整阅读之前先获得清晰的判断；文末再用「写在最后」收束。完整形态见下方「输出结构」，定型自 Notion 范本（Fiona Fung 那期），是当前的标准模板。

---

## 形态变体：单人演讲实录（精修版 + 配图）

> **适用场景**：源视频是**单人演讲 / keynote / 大会分享**（非多人访谈），但用户希望**保留演讲者第一人称语气与金句**，而不是按主题重构成图文精读。这是介于「图文精读」（重构）与「对话体逐字稿」（多人还原）之间的**第三种形态**。判断依据看源材料：单一说话人、有幻灯片、价值在"他原话怎么说" → 走本变体。

**核心做法：以演讲者本人的话为正文，但不照搬生口播——**

- **保留**第一人称语气和金句（演讲的锋利句子、比喻、口头禅照原意留住）。
- **清掉**口水词（um / uh / you know、无意义重复、自我打断）。
- **理顺**跑题、绕回去又说一遍的地方，让逻辑连贯；允许合并相邻的同主题碎段。
- **按幻灯片分段锚定**：每一节对应一页 / 一组关键幻灯片，节标题点出该段核心，并在对应位置插入 **PPT 截图占位**（沿用下方「媒体占位符」规则）。
- **不重构主题顺序**：与对话体一致，按演讲原始时间线推进，不打乱先后。

**与对话体的差异**：单一说话人，**无需 `>>` 说话人切换核对**；正文不再是"说话人 + 时间戳"的一问一答，而是按节承载的第一人称实录段落。但**其余规范全部沿用**——导读层（开篇金句 + 导语 + 嘉宾背景 + 核心观点）与文末「写在最后」、翻译质量双底线、去 AI 味自检、审稿人自检 Checklist、面向发布的多轮精修流程、外部素材处理、Step 2.5 字幕核校与专名核对铁律，一个都不少。

**文件命名**：`<生成的中文标题> - 演讲实录.md`，存放规则同对话体。

**复合用法——「现场回闪」**：同一场大会（如 Cursor Compile）多位嘉宾就**同一问题**各自分享时，可把多篇单人演讲实录并入**一篇**，以"现场回闪"形式呈现：

- 开篇用价值传播段交代语境——"在某大会现场，N 位来自不同领域的嘉宾回答了同一个问题，我们通过上 / 下篇为你呈现"，营造"亲临分享会、听不同视角碰撞"的观感。
- 正文以「**上篇〈视角 A〉— 嘉宾1** / **下篇〈视角 B〉— 嘉宾2**」分节承载各自的演讲实录，每篇仍各自保留金句与配图。
- 共享一个总标题与导语；各嘉宾的「嘉宾背景 / 核心观点」可在各自分节内就近给出，避免开头堆叠。

## 编辑原则

**做什么：**
- 准确标注每一段话对应的说话人（主持人 / 嘉宾 / 提问观众）
- **工作稿**在每段对话前标注时间戳，格式为 `[MM:SS]`；**发布形态去掉时间戳**，且必须在机检全绿之后再去（见「关于时间戳」）
- 去掉广告 / 赞助商读广告段落（如 RAMP、WorkOS 等品牌推广内容）
- 去掉这几类无信息内容：纯语气词（"um"/"uh"/"you know" 的冗余堆叠）、**开场与结尾的寒暄**（"谢谢邀请""感谢你来上我们的播客""谢谢你抽时间"）、**说话人边想边说的过程**（"这个我有一大堆反应""那句话怎么说的来着"）、**纯附和回合**、笑声等舞台提示（`[笑]`）、广告口播，以及对内容没有帮助的闲聊
- **但让步与限定语必须保留**：`我说话会比较小心`、`我不确定你躲得开`、`这不是说它没有价值` 这类自我收口是立场的一部分，删掉等于把话说硬了（见「删减红线」第 4 条）
- 修正明显的语法错误和自动听写误差（如人名、公司名、术语拼写）
- 保留对话的自然节奏：追问与被打断的半句照留（打断处用 `——` 收尾）。**但不保留 `[笑]` / `[掌声]` 这类舞台提示**，它们在成稿里只是噪音；语气若真的重要，靠嘉宾自己的措辞承载

**不做什么：**
- 不重构对话顺序——严格按照原始时间线排列
- 完整存档版不删减对话；但面向公众号发布的**精编版**要按下方「面向发布的精编压缩」原则压缩（删冗余、留核心）
- 不替换嘉宾用词——即使嘉宾的表述不够"学术化"，也要保留原意
- 不在对话行内插入编辑评论或注解——对话本身是中性记录，不是解读。编者的话只能出现在三个**指定容器**里：`💡` 提炼行（全篇 1-3 处）、「写在最后」收束段、以及外部素材的「📎 延伸」块（若该篇未走并入协议、仍保留延伸块）。三者之外一律不得夹带编者观点，尤其不得改写嘉宾原话来表达编者的意思
- 不将对话内容改写为段落体——保持一问一答的对话格式

## 面向发布的精编压缩

谈话类逐字稿的完整版往往太长，不适合直接发公众号。面向发布时，要在**保留核心内容**的前提下做精编压缩。

- **删**：铺垫性的长问、纯附和回合（如"对，完全是这样""没错"）、广告 / 赞助口播、重复论证、绕回去又说一遍的内容。
- **留（尽量保原话）**：真正有来有回的关键问答、生动的例子、故事、金句、关键技术判断。
- **接**：段落之间的过渡只在必要处用编辑自己的话补一句，主体仍保持对话体（说话人标签 + 发言）。
- **并**：合并相邻的同主题小节，避免分段过碎，一篇约 8 节为宜，而不是 15-20 节。

### 主持人回合：保留转场与追问，只删纯附和（2026-09-21 用户口径，取代此前「只留真正的提问」）

> **为什么改**：此前对齐 Z Finance 的做法，把主持人压成一句干瘪的问句，读者会觉得话题是突然跳过来的。主持人的提问同时承担「转场过渡」，这层作用不能砍。InfoQ 编译 Neil Movva 那期保留了主持人的承接与追问，读起来顺得多，作为新参照。

- **删掉纯附和与不带新信息的复述**：单纯附和（"对""没错""他们在睡觉。"）、主持人把嘉宾刚说的话原样换个说法重复一遍且没有新信息的回合，直接删；被拆开的嘉宾发言合并成一段。
- **保留承载逻辑的转场与追问（强制）**：主持人的提问要交代为什么问这个、承接上一段说了什么、指向下一段要谈什么。这类回合**不得压成一句干瘪的问句**，宁可保留完整的两三句（承接 + 追问）。例：❌"这也是为什么聊得很深之后，效果会开始变差？" → ✅"这也是为什么有时候对话变得很长以后，大家会感觉模型能力开始退化，背后其实有技术原因？"
- **补足指代与因果，不改变立场**：问句里的"这个""那""它"补成读者能独立读懂的说法；补的只能是原话里已有的上下文，不得替主持人加上他没表达过的立场或论据，改完回字幕核对语气强度。
- **主持人的复述里若带了真实的质疑或新信息，改写成问句，不要直接删**：例如"那很糟，95% 可用性的数据中心基本零买家"改成"95% 可用性的数据中心基本没人买，你为什么要？"——**改写只能压缩句式，不能替主持人加上他没表达过的立场或论据**，改完要回字幕核对语气强度没有被抬高或降低。
- **"聊聊 X""继续讲讲 X"这类引导语，改成具体的提问**（"聊聊电力" → "电力这一层呢？"），让每个 `🎙️` 段落都有一个明确的问题，前面可带一两句承接。
- **删掉回答开头的口头禅**：正是、对、没错、完全正确、是的、说白了、绝对是——这类词删掉后句意不变，回答直接从判断讲起。**保留嘉宾用来让步或收口的词**（"大概可以""我确实这么认为"这类带立场信息的开头不算口头禅，不要跟着删）。
- **判断标准同「删减红线」**：删掉的必须是真的不带信息，改写不能扭曲立场强度。拿不准时保留，交给 Agent Council 复审。

完整存档版与发布精编版可以并存。发布精编版按「输出结构」走：正文不设「以下为完整逐字稿」这类总标题，直接由各章节 `#` 标题承载。

### 删减红线：时间轴缺口扫描（强制 · 压缩之后立即做）

精编压缩最危险的失败模式不是删多了几句，而是**整段关键问答被静默删掉、且自检时看不出来**——因为成品读起来依然连贯。所以压缩完成后，进入 Step 2.5 之前，**必须做一次时间轴缺口扫描**：

1. **用脚本扫，不要靠眼睛**：

   ```bash
   python3 check_transcript_edit.py "output/<标题>/<标题> - 逐字稿.md"
   ```

   它会自动在同目录找 `transcript.json`，列出**所有被删的连续 ≥2 分钟区间**（含开场与片尾）、摘出每段的原字幕，并顺带校验时间戳是否单调递增（出现逆序即 exit 1，属硬伤）。含让步 / 限定语的区间会标 🔺 高风险——那正是第 4 条要防的那类删除。
2. 对脚本列出的每一个区间，逐一写明删除理由，且理由**只能落在这四类**：广告 / 赞助口播、铺垫性长问、重复论证（绕回去又说一遍）、纯附和回合。脚本只负责把区间算出来、把原字幕摆到你面前，**判断该不该删仍是编辑的活**。
3. **凡不属于这四类的区间，一律补回**，不接受"篇幅太长""不够重要"这类理由。判断依据回到上面的「留」：真正有来有回的关键问答、生动的例子与故事、金句、关键技术判断。
4. **删减改变立场强度的，等同硬伤**。嘉宾的让步、限定、自我收口（"当然也有例外""我不否认这一点"）被删掉，会让她的观点显得比原话更硬，这属于扭曲，必须补回。
5. 扫描结果写进交接文档的「✅已完成」，形式为：`缺口扫描：删除 N 段，均属广告/铺垫/重复/附和；补回 M 段（列出时间区间与原因）`。

> 实例教训：某期 72 分钟访谈的精编初稿静默删掉了 `[50:22–52:54]` 整段，而那是全片**唯一**正面回答"AI 实验室抢人时我们凭什么"的问答，也是该篇标题主线的正面对照；同轮还删掉了嘉宾对 AI 生成内容的让步段，使其立场比原话更硬。两处都是靠交付前的 Agent Council 才捞回来的，初稿自检完全没有察觉。

## 说话人识别规则

1. **从视频标题、频道信息和对话内容推断说话人身份**
2. 字幕中的 `>>` 符号或 `[SPEAKER NAME]` 标记说话人切换；**`>>` 标记须逐一核对**：短插话（接话、替对方补完半句、吐槽）必须单独成段归属其人，不得因语义连贯就并入长答主的发言——下一句若以 "Exactly / 没错 / 对，完全是这样" 开头，往往说明上一句出自对方之口
3. 通常提问者 = 主持人，回答者 = 嘉宾
4. 在文档开头明确列出所有说话人及其身份
5. 学生 / 观众提问时，标注其姓名（如有自我介绍）和身份（如"MBA 学生 Brandon"）

## 翻译质量与受众平衡

逐字稿面向**多元受众**：既有 AI 从业者，也有教育者、研究者、文科背景的普通读者。翻译时必须同时满足以下两点：

1. **专业性**：核心术语必须使用行业标准翻译，不能用口语化的近义词替代。
   - 保留高共识词汇的英文原貌：Token、Agent、GPU、API、Prompt、Transformer 等。
   - 涉及具体研究、产品、模型名称时，首次出现保留英文原名（如 Project Glasswing、Mythos、Claude Code），可在括号内补充简要说明。
   - 对从业者熟悉但大众陌生的概念（如 "revealed preferences"、"comparative advantage"），首次出现时在括号内补充中文解释。
2. **可读性**：句式要顺畅、自然，避免英式语序直译。
   - 长句要按中文断句习惯拆分，但不能丢失原句的递进 / 转折关系。
   - 嘉宾的自嘲、玩笑、口头禅，要用中文里能传达相同语气的表达替换，而不是字面翻译。
   - 涉及人物比喻、场景描写时，优先保留嘉宾原话的画面感（例如"独角兽 vs 鸭嘴兽"这种比喻不要简化为"两件不同的东西"）。

**翻译质量底线**：从业者读了不觉得幼稚或不准确，文科生读了不觉得晦涩或被排斥。

## 输出结构

> **共有壳（开篇金句 / 主图 / 署名行 / 导语 / `# 嘉宾背景` / `# 核心观点` / `# 写在最后`）、全部排版约定（`#` 标题、禁 `---`、空行规则、说话人标签与 emoji 约定、`>` 与 `💡` 的分工、媒体占位符）、以及去 AI 味清单，一律见 `skills/publication_format.md`，那里是唯一来源。本节只写逐字稿形态特有的部分。**

### 关于时间戳（逐字稿特有 · 重要）

发布形态**不带 `[MM:SS]` 时间戳**。但时间戳是 `check_transcript_edit.py` 做缺口扫描的唯一依据，去掉之后那道防线就失效了。因此固定流程为：

1. **生成与精编阶段带时间戳**，正常跑 Step 2.5 的机检（时间戳单调递增 + ≥2 分钟删除区间扫描）。
2. **机检全绿之后，再统一去掉时间戳**转为发布形态。顺序不可颠倒——先去时间戳等于跳过机检。
3. 转为发布形态**之后**若还要做删减或结构调整，**机检返回"成品里没有时间戳，无需扫描"不构成通过**（那是跳过，不是放行）。必须回 `transcript.json` 人工对照核校，并在交接文档写明删了哪几段、理由属四类中的哪一类。
4. 外部素材的时间戳照旧保留（写法见「外部素材的时间戳写法」），不受本条影响。

### 5. 正文各章节

核心观点之后直接进入正文。**每章一个 `# 标题`，不加 `## ` 子标题、不加 `---` 分割线**，靠标题本身分节。

#### 章节标题：要短、具体、点出核心

1. **标题必须是判断句，不用功能性 / 描述性标题**（❌"关于 AI 安全的讨论"、"嘉宾对监管的看法"）。判断句意味着标题本身就是一句可以为真或为假的话，读者不看正文也能提前判断"这一节我是否需要"——参照 Z Finance 编译 20VC（OpenRouter Alex Atallah）那期的标题写法（如「推理服务商不会轻易变成商品」「路由不是时髦功能，选择权才是产品」）。
2. **要短，但必须具体点出这节讲什么**，不能为了短就写成空泛的悬念式标题。
   - ❌ `说到底，只有一个问题`（没说清是什么问题，等于没说）、`一些意外的发现`
   - ✅ `别把"动起来"当成"有进展"`、`管理者把"盯全局"交给了一个常驻的 Claude`、`成本在崩塌，时间表却最难预测`、`没有坏芯片，只有坏价格`
2.5. **判断句优先直接取自正文的强 quote，而非编辑归纳句**（2026-09-22 用户口径）。先看该章正文里有没有嘉宾说过的、已经加粗/高亮的强判断句，能直接摘用就摘用，不要另起一句更平淡的编辑概括；只有正文没有现成强句时才自己拟一句判断句做标题，拟出的句子也要往"够呛、够有话题度、拿出去就能单独当 quote 转发"这个方向使劲，不要写成安全、四平八稳的归纳。（实例见 [Neil Movva - Making AI 10x Cheaper](../output/Neil%20Movva%20-%20Making%20AI%2010x%20Cheaper/交接文档.md) 第 26 轮：`GPU 只能在吞吐和延迟之间选一边，他选吞吐`、`没有坏芯片，只有很坏的价格`、`我就是第一个买家，我会买 95% 可用性` 均为正文原句或极接近原句。）
3. **单级标题：全篇只用 `#`，不设 `##` 子标题**（2026-09-22 用户口径，**推翻 2026-09-21 定的 H1+H2 两级方案**——两级读起来太碎）。约 8–10 章，每章对应一段完整的对话主题块（可能跨 5–15 分钟，不按固定时长切），标题是能覆盖全章内容的判断句。章数按对话主题块的自然边界定，**若两个话题紧邻且共享同一论证脉络，宁可合并成一章也不要拆成两个平行 H1**（例：GPU 吞吐/延迟取舍与软件降本方案合并为一章）。每章篇幅按内容自然长度定，不强行拆分或注水凑数。
4. **定稿前每个标题都要回字幕原句核一遍**（规范见 `publication_format.md`「怎么验」）。标题是压缩层，和核心观点、导语同属硬伤高发区：**它必须由它所概括的那段字幕支撑，而不是由你写好的中文正文支撑**。重点查两样——① 标题有没有把嘉宾的论点说反（把她认为"能改变的"写成"不能改变的"，反之亦然）；② 标题的断言有没有被同篇正文的另一句当场证伪。
5. **一节只扛一个主题**。若一节里有明显的"第二拍"（嘉宾自己说了"另外还有一个教训""顺着这条线我想问"，或主持人另起一问），那就是天然的拆点。拆完必须回 `transcript.json` 对照该时间点确认是真的话题转折，并在交接文档写明动了哪几节。
6. **标题里不用第三人称指代嘉宾**（❌「GPU 只能选一边，他选吞吐」→ ✅「……我们选吞吐」）：逐字稿是对话口吻，「他」会把读者拉出对话（2026-09-24）。
7. **标题必须盖住整章内容**：若标题只对得上本章前半，**优先移动章节边界（把 H1 挪到话题转折处）或换标题，不靠增加章数解决**；全篇章数约 10-11 章上限（用户 2026-09-22 要求「别搞出十几个一级标题」）。名词短语标题要补齐助词（❌「Transformer 原罪」→ ✅「Transformer 的原罪」）。

#### 对话格式与插入物

说话人标签格式、emoji 约定、空行规则、`>` 与 `💡` 的分工、媒体占位符——全部见 `skills/publication_format.md`。逐字稿另有两条特有约束：

- **正文不带时间戳**（见上方「关于时间戳」）。
- **拆节 / 调整结构时，不得为新起的一节编造主持人提问。** 主持人没问过的话不能塞进他嘴里，这和把外部发言错归给嘉宾是同一类错。新节可**直接由嘉宾的发言起头**——范本中「砍掉没用的流程：JIT 即时规划」一节正是此写法。若确需过渡，用编者的 `💡` 提炼行，不要伪造问句。

### 6. 写在最后

见 `skills/publication_format.md`。成品不写「本文来源」；外部素材声明按「外部素材处理」一节的要求记进交接文档。

## 输出语言

- **全部翻译为简体中文**。无论原视频是什么语言，最终输出的逐字稿内容必须是中文。
- **说话人标签规则**：第一次出现说话人时使用完整姓名（如 Daniela Amodei、Patrick O'Shaughnessy）；之后再次出现时使用名字（如 Daniela、Patrick）。
- **行业专有名词处理**：
  - 保留高共识词汇的英文原貌（例如 Token、Agent、GPU、API、Prompt、Transformer、Scaling Law 等）。
  - 对较新或特定行业的概念词，第一次出现时在后面用括号补充中文解释。
  - 公司 / 产品 / 项目代号保留英文原名（如 Anthropic、Claude、Project Glasswing、Mythos）。

## 去 AI 味（强制自检）

定稿前扫一遍，删掉一眼就是"AI 写的"的词与句式，保持冷静、有判断力的编辑语感。

- **尽量不用破折号（——）**：破折号密集是最典型的 AI 痕迹，用逗号、句号或分句替代。
- **少用"不是…而是…"**：这个句式一篇里出现两三次就够，过多即 AI 腔。
- **禁用包装词**（举例）：值得一提的是、不难看出、综上所述、换句话说、某种程度上、令人瞩目、难得地。
- **禁用空转连接**："首先 / 其次 / 最后"式机械罗列、"不仅…而且…"滥用、排比句轰炸。
- **原则**：用具体事实代替形容词；能删的过渡句直接删；嘉宾原话可口语，编辑旁白要书面克制。

## 完成后必须执行：审稿人自检

整篇文章生成完毕后（包括开篇金句、导语、嘉宾背景、核心观点、正文各章节、写在最后），必须切换到**资深编辑/审稿人角色**，对全文进行一次系统性自检。检查清单如下：

### Checklist A：嘉宾背景准确性
- [ ] 嘉宾的身份、职位、所属机构是否准确？
- [ ] 教育背景、过往履历是否有编造或夸大？
- [ ] 所有事实性陈述都能在字幕中找到出处或属于公开可核实信息？

### Checklist B：开篇金句、导语与写在最后
- [ ] 开篇金句是否来自嘉宾本人原话？是否真的是这篇文章里最具判断力的一句？
- [ ] **金句是否被导语末尾与「写在最后」两次呼应**（题眼共出现三次）？
- [ ] 导语段是否清晰传达了"为什么这场对话值得花时间读"？
- [ ] 「写在最后」是否落在具体行为上、未替嘉宾总结出他没表达过的立场？
- [ ] 是否避免了把"内容摘要"和"价值判断"混为一谈？

### Checklist C：核心观点完整性
- [ ] 核心观点是否覆盖了视频中所有重要的话题脉络？
- [ ] 是否有遗漏的重要论述（特别是嘉宾首次公开分享的独家信息 / 数据 / 决策）？
- [ ] 每条核心观点的概念命名是否准确、有辨识度？

### Checklist D：逐字稿翻译准确性
- [ ] 每段中文翻译是否忠实于英文字幕原意（不增、不减、不歪曲）？
- [ ] 说话人标注是否与原字幕一一对应？
- [ ] 工作稿的时间戳是否准确？发布形态是否已在**机检全绿之后**才去掉时间戳？
- [ ] 说话人 emoji 是否全篇一致、且未凭姓名推断性别？

### Checklist E：标题与内容对应
- [ ] 每个章节标题下的对话内容是否真的围绕该标题展开？
- [ ] 是否存在"挂羊头卖狗肉"的情况（标题暗示 A，但内容主要是 B）？

**自检发现问题必须立即修改**，不要把问题留到下一步。自检完成后，向用户简短汇报自检结论（哪些项通过、哪些项有调整、调整了什么）。

## 面向发布的多轮精修流程（交付初稿之后）

初稿交付用户、用户听完原片提意见后，进入**协作精修**。**固定按以下顺序改，每处改动都对照字幕核校（Step 2.5 精神）：**

1. **外部素材并入**（在正文层处理，因为只有正文才有结构调整）。
2. **正文**：结构 / 合并 / 删减 / 调序。
3. **非正文**，子顺序固定为：**核心观点 → 导语 → 嘉宾背景 → 写在最后**（与 `publication_format.md`「生成顺序」一致：核心观点提炼自正文，导语又要基于正文与核心观点，所以核心观点必须排在导语之前）。
4. **最后**才做标题 + 钩子。

> 删某节时检查它是否是后文铺垫；若是，把后文依赖它的句子改成不依赖前文的版本（与本 skill「面向发布的精编压缩」呼应）。

### 用户在 Notion 上留评论时的处理流程（2026-09-24 沉淀）

1. **先读全部评论**（`notion-get-comments`，带 `include_all_blocks: true`），按三类分：直接改（错别字、标点、体例）/ 需回字幕核原声（用词、数字、指代）/ 需用户拍板（标题、增删整段、加图）。
2. **用户质疑用词或数字**：先回 `transcript.json` 核原文。原文站得住 → 保留，并在该评论下回复**一句原声引文 + 一句理由**；用户仍坚持要改 → 照改，不争第二次（只举证一次），改时挑不引入原文没有含义的替代词（例：「平衡着生长」→「牵制着生长」，避开「制衡」的对抗意味）。
3. **每条评论都要有回复**（改了什么 / 为什么不改）。评论没有 resolve 接口，回复即闭环，由用户自己点「解决」。
4. 一次批量改完，**读回线上稿逐条核对**（做法见 `notion_publish.md`「精修阶段操作坑」）。

### 删减与去重原则（2026-09-24 用户口径）

- **只挑重点**：保留强科普性、有具体画面或数字、可传播的内容；直接删抽象背景、情怀式铺垫、与主线关系弱的段落，不为「完整」而留。
- **去重**：嘉宾反复强调的同一核心主张（如「做最便宜的 Token」「拾荒者打法」）只留最强的一次，其余整句或整轮问答删掉。删后检查衔接：**主持人的提问优先压成一句短问，而不是整句删空**（整句删会让下一句嘉宾回答突兀）。
- **用户亲手删掉的内容，Agent 不以「忠实度」为由建议补回**；只有当删除造成事实或指代错误（例：删掉嘉宾结论后主持人「为什么？」失去落点）时才**提示**，恢复与否由用户定。
- **用户手改过的位置视为有意决定**，终审前先看「已做决定」清单（见 `reader_facing_review.md`）。
- **引用外部信源（官方图、新闻截图）**：直接用官方图 + 一行短图注（指标定义、日期、来源链接），不再写长译者注；配新闻截图时**必须标注指标口径与发布日期**，口径不同的数字不得并列当同一件事（例：xAI 的模型 FLOPs 利用率与 Cast AI 的集群 GPU 利用率是两个指标）。


## 外部素材处理（字幕之外的资料）

素材不限于视频字幕，还包括**推特 / 文章 / 官方发布页 / 他人解读 / 嘉宾其他演讲 / 嘉宾在别的对谈里的发言**。

默认**当"外部事实"处理，不混入对话体**。**唯一的例外**是「嘉宾在别的对谈里就同一话题的发言」——这一类允许并入嘉宾的发言，但必须走下方的 **A/B 双 Agent 并入协议**，不得直接动手。

| 素材类型 | 可以怎么用作补充 |
|---|---|
| 视频字幕（主源）| **唯一**可成对话体的来源 |
| 嘉宾 / 主持人自己的总结贴（如 Lenny 的 takeaways 推文）| 校准标题 / 核心观点 / 内容与价值；捞回正文遗漏的高光素材 |
| 官方发布页 / 新闻（如某产品发布）| 给文中提到的产品补一句"它到底是什么"的事实底注 / 图注 |
| 第三方解读（视频 / 文章）| 仅作背景佐证 / 配图来源，须标明"第三方"，勿当官方口径 |
| 嘉宾其他演讲（如 Keynote）| **幻灯片截图配在对应小节**；净新增口述若无对应 slide 又不能并进对话，则放弃 |
| 嘉宾在**别的对谈**里的发言（另一档播客 / 圆桌）| 可作「延伸」引用块补机制；**经用户同意也可直接并入嘉宾发言**，但必须先过 **A/B 双 Agent 并入协议**（见下） |

**呈现形式**：优先 **截图 / 视频 + 图注**，或克制的编者底注；**不用打断观感的"XX 补充"灰框**；第三方或无据来源标 `⚠️建议人工核对`。

### A/B 双 Agent 并入协议（把外部发言并进嘉宾原话时强制）

把另一场对谈里的发言**并进本篇嘉宾的发言**（并入后读者分辨不出是别处说的），必须拆成两个**不同的** Agent 依次执行，**不得由同一个 Agent 既核实又并入**——自己核实自己等于没核实。

**第 0 步 · 候选池核实（在 Agent A 之前，主模型自己做）**

候选内容从哪来，本身就要核。**不得直接采信用户或任何二手来源对该外部源的描述**——包括"这段是谁说的""他提出了什么框架""在哪一期哪一段"。做两件事：

1. **核链接**：抓取该源，确认标题、时长、内容与描述一致。抓不到或对不上，退回问清楚，不进候选池。
2. **核描述**：用户说"某某观点是嘉宾提出的框架"这类判断，一律回原始素材验证后再用；**验证不了就不进候选池**，更不要顺着这个前提往下推理。

> 实例教训：本项目某篇的三处错归，源头不在字幕，而在主模型接受了"某分析框架是嘉宾自创的"这一二手描述——链接核过、标题对得上，唯独没核这句描述。结果整个框架属于该期主持人，错误一路带进候选池、带进初稿，直到 Agent Council 才捞回。**链接对不等于描述对。**

**Agent A（核实 · 先跑）**：逐条判定候选内容，**两道闸门必须同时通过**才放行。

1. **归属闸**：该条确为**嘉宾本人所述**，不是同场主持人或其他嘉宾的话。判定方法见下方「说话人归属铁律」。**判不出来的一律不放行。**
2. **相关闸**：该条与拟并入的**那一节**强相关——是对该节已有论点的机制补充或证据补充，而不是新开一个话题。并入后**不改变本节的论证走向、不打乱时间线、不需要为它另起一段铺垫**。判据是：把它接进去之后，那一轮发言读起来仍是一个人在连贯地说同一件事。**只要需要"为了容纳它而调整结构"，就不放行。**

Agent A 输出一份清单，每条写明：`原文位置（拟并入哪一节 / 哪一轮）｜候选内容｜归属判定与依据｜相关性判定与理由｜放行 / 不放行`。

**Agent B（并入 · 后跑）**：**只拿 Agent A 放行的条目**执行，不自行增补、不自行改判。工作是把这些内容改写成**第一人称**、接进嘉宾对应那一轮的发言，语气与上下文拉齐，读起来是连续的一段话。**A 没放行的一条都不许并。**

**若用户推翻 Agent A 的不放行裁决：**

用户有权决定保留 A 判为不放行的条目，这是编辑决定。但推翻时**必须同时做两件补偿动作**，否则等于把一次有记录的例外伪装成一次全票通过：

1. **交接文档里的外部素材清单逐项列全**，把被 A 判不放行、而用户保留的条目也写进补入清单，一条不落。正文既然不区分来源，这份清单是唯一的追溯入口，少列一项那项内容就彻底无从追溯。
2. **交接文档记录 A 的原始判定与用户的裁决**：写明哪几条 A 判不放行、理由是什么、用户决定保留。接手的人打开稿子时，默认认为所有内容都过了 A 的闸——不写就是误导。

**并入之后仍然必须做的两件事：**

- **交接文档保留合并声明**：写明本文为双来源合并整理、具体补入了哪几处、这些内容为嘉宾本人所述但并非在本次访谈中说出、以及同场其他人的观点未被引入。正文既然不再区分，这是全篇唯一的来源自证，**不得删除**。
- **数字与预测类内容保留原始日期锚**：金额、占比、增长预测，以及"我目前不担心 X"这类当下判断，都会过期，必须带上原始时间口径（正文或图注）。机制类内容不受此限。

### 说话人归属铁律（Agent A 的归属闸判定方法）

并入**另一场多人对谈**（另一档播客、圆桌、对谈节目）的内容时，**每一条都必须先定案说话人，再决定要不要用**。自动字幕在这类素材上极不可靠：`>>` 常常只标声学事件（笑声、清嗓）而不标换人，长段对谈可以整段没有任何换人标记。

- **无 `>>` 标记的区段，必须用内证判定归属**，可用的线索包括：称呼语（直呼对方名字，如"…issues **Bill** that I raised…"）、指向性表述（"**你** 18 个月前提过"、"in response"、"to your point"、"I listened to **you** and…"）、身份自陈（自述常上某节目、自述持仓）、以及立场差（谁在唱多、谁在示警）。
- **必要时用文体计量交叉验证**：统计口头禅在各人**已确认轮次**中的分布（如句末 `right?`、特定术语），再看争议段落落在谁的分布里。
- **拿不准的一律不引入。** 不得因为"语气像""思路像""符合他一贯观点"就默认属于嘉宾——**越像，越危险**，因为读者同样分辨不出。
- **兜底声明要写实**：交代外部素材来源时必须写明范围（如"仅含 X 本人发言，该期主持人的观点未被引入"），不能笼统写成"来自 X 的发言"——笼统的声明会把个别错归放大成全篇错归。
- **仍以「延伸」引用块呈现时**，引注一律指向被引句首，不指该轮起点，方便读者回原片核对。

> 实例教训：某期把另一档播客里**主持人**提出的分析框架（交易连续谱、"若没有这笔投资这些产品还会被买走吗"、"只有一个买家的芯片"）连同"作为某公司股东我并不担心"一并写成了嘉宾的判断，等于替嘉宾虚构了持仓身份与核心框架；三处错归全部由 Agent Council 才捞回，初稿自检毫无察觉。定案依据是主持人开场自报议程时的称呼语、以及嘉宾接话时的"in response"。

### 外部素材的时间戳写法

外部素材自带的时间戳**不得写成 `[MM:SS]` 方括号格式**，须写成 `（<来源缩写> MM:SS）`（如 `（BG2 10:31）`）。两个原因：① `check_transcript_edit.py` 会把方括号时间戳当成主源时间轴解析，制造假的"逆序"硬伤和幻影删除区间；② 读者会把它读成同一条时间轴。

### 外部素材的时效标注

跨时间引用时分两类处理：**机制类**（原理、会计路径、历史对照）不会过期，正常引用即可；**数字与预测类**（金额、占比、增长预测）以及**"我目前不担心 X""我现在会买"这类当下判断**都会过期，必须在正文与图注中显式标注原始日期，且不得当成嘉宾此刻的立场。图表尤其要标——图会被单独截出去传播。

## 标题与钩子（精修最后一步）

- **至少给 5 个标题 + 各自配一个钩子**；**每个钩子 ≤ 20 字**。
- 可用嘉宾背景做信用钩子（如"管着 X 和 Y 的人"）；
- **标题别和导语 / 首句撞词**；避开"如何打造…教你…"教程腔；
- 可借嘉宾 / 主持人上节目后自发的 takeaways 反向校准标题与价值。
