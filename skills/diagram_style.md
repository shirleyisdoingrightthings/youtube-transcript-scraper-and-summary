# 配图规范（Diagram Style · 手绘工程图）

> **调用方式**：给成品配图、画机制示意、把一段技术描述变成图时，加载并执行本规范。
> **定位**：图是正文的一部分，受同一条忠实度红线约束——**图上每个数字都要先核到源头再画，没核实的不画**；而**出处本身不进图**，一律集中到成品文末（见 §五）。
> **配套**：正文格式看 `publication_format.md`；字体与子集化工具在 `assets/fonts/`（含 README）。

---

## 一、先判断该不该画

一张图值得存在，只有一个理由：**它让冷读者一眼看见一个机制，而那个机制用文字描述读者得自己在脑子里拼**。如果一句话说得更快，就写那句话。

**画机制，不画名词。** 一个写着「缓存」的方框，信息量低于同一句话的正文；而请求穿过它的路径、它夹在哪两级存储之间、拿掉它之后哪条箭头会消失，才是文字给不了的。

**一条逻辑链能画进一张图，就不要拆成四张。** 拆图的代价不是画得多，是**读者的耐心**：一节里连着四张图，读者会开始跳过；而后面每一节都会跟着通货膨胀。判据是「这两张图是不是同一个层级的同一条链」——是就合并，不是才拆。本项目踩过：一节里放了四张（token 循环 / 芯片解剖 / 对应表 / 批量），其中前三张其实是同一条链的三段，合成一张之后信息一点没少，图少了两张。**真正该拆的分界是「换了一个轴」**：一次前向的空间路径 vs 跨请求的批量与时间，这两件事塞进同一张就是 §二 说的那种失败。

**横版优先，慎用竖版。** 竖版能把字放大（同样内容，800 宽比 1080 宽的画布字大约 35%），但**读者是往下滑的**：一张滑很久滑不到底的图会耗掉耐心，而横版的篇幅是一眼可预期的，读者可以自己决定点不点开看大图。所以**先靠合并与减量把密度降下来，再考虑放大字号**，不要靠拉长画布换字号。**器件类的图更不能转竖版**——芯片本来就是横的，转竖就是画错构造。

**比较方案就画差别。** 两种架构并排、一前一后、每个选项各自增删的那条边，读者要能指着说「我在这两者之间选」。**几个互不相连的方框各写一个选项，那不是比较，是把选项列表重排了一遍。**（这条是我们踩过的坑：曾把三种芯片并排画成三个卡片，用户当场指出「这三个图都画得不怎么样」。）

**复杂度对着赌注给。** 一跳的问题就是三个方框；把写入改道到队列的迁移，就得画出队列、写方、读方和那条定序箭头。

**给箭头写标签。** 没标签的箭头等于「有某种关系」；`写入` / `失效` / `每 30 秒轮询一次` 才是信息。

## 二、动笔前的四步（借鉴 coleam00 的 Excalidraw skill）

1. **判深度**：这张是**概念图**还是**技术图**？两者的信息密度与验收标准完全不同。概念图求一眼懂，技术图要经得起同行拿数字对。**先判完再动笔**，不要每张都按技术图画。
2. **判层级（多层缩放）**：Level 1 主干流程 → Level 2 分区边界 → Level 3 区内细节。**一张图只画一个层级**。把 Level 3 的细节和 Level 1 的主干塞进同一张，是最常见的失败方式。
3. **列分镜**：一篇稿子先列 4–8 张图的分镜表，每张写清「主题 / 要说明的那个判断 / 结构类型 / 关键标签」，**给用户过一遍再动手画**。逐张画完再返工的代价高得多。
4. **画完必须自己看渲染结果**。这一步是强制的。本项目已经因为跳过它连续出过三次错：晶圆画成了普通切割晶圆（与 Cerebras 的做法正相反）、自闭合标签被脚本改坏、SVG 表现属性里的 `var()` 在部分浏览器不生效。**没看过渲染结果的图不算画完。**

## 三、手绘风格规格（唯一风格，不再另起）

参照 Excalidraw 的观感，但不依赖 Excalidraw、不引渲染管线。

### 线条

用 [`rough.js`](https://github.com/rough-stuff/rough) `4.6.6`，从 `https://cdn.jsdelivr.net/npm/roughjs@4.6.6/bundled/rough.js` 载入（**jsdelivr 在 Artifact 的 CSP 白名单内，cdnjs 上只有过时的 3.1.0**）。

- 基础参数：`roughness: 0.5–0.6`、`bowing: 0.5`、`strokeWidth: 1.4–1.8`。
- **必须开 `disableMultiStroke: true`。** rough.js **默认每条边画两遍**，那正是「方框边缘像涂描了很多次」的来源。单笔一画，框就干净了。
- **必须开 `preserveVertices: true`。** 否则线端会被随机化，拐角处笔画戳出去——就是「有些笔画突出来了」那个毛病。
- **单笔比双笔看着细，线宽要补一档**（普通框 1.7、容器 1.5、小色块 1.2、强调 2.0）。
- ⚠️ **一条反直觉的事实：Excalidraw 那种圆滑方框不是「更手绘」，是更不手绘。** Excalidraw 内部用的就是 rough.js，它的 sloppiness 滑块就是 `roughness`：Architect 档≈0（干净单线）、Artist / Cartoonist 档才是我们原来那种。参考样本里那些漂亮的圆角框是 Architect 档。**想要那个观感，不是去装 Excalidraw，是把 roughness 调下来、关掉多笔。**
- **方框一律走圆角**。`rc.rectangle()` 没有圆角，要自己拼圆角路径再交给 `rc.path()`：这是 Excalidraw 观感的一半，直角框看着就"不是手画的"。半径 10–16，小色块 3–6。
- **填充默认 `fillStyle: 'solid'` 的浅色 tint**（见下方颜色表的 fill 列）。**不要用 hachure 填带文字的方框**——文字压在斜线网底上读不清，这是本项目踩过的坑。hachure 只留给刻意要表达"纹理 / 不可数"的少数场合。
- **虚线 = 逻辑分组、边界、容器；实线 = 具体部件。** `strokeLineDash: [9,7]`。读者要能一眼看出哪一圈是"这些东西属于同一块地方"，哪一个框是"一个真实的部件"。
- **同一张图里，虚线不承担两种以上语义。** 已经用虚线画了分组框和对比边，就不要再画满幅虚线网格——读者得先分辨「这根虚线是坐标参考还是在说事」才能看内容。**坐标网格优先用轴上的短刻度**（轴外 6px 一小段 + 标签），位置照样读得出，图面干净得多。（用户 2026-09-07 当面指出。）
- **区域属性用小徽章（pill）标**：圆角 10、高 21、字号 10.5，例如 `片内` / `片外`。比在旁边写一行说明省地方，也更像工程图。
- **必须固定 `seed`**，否则每次渲染换一张脸，重新发布时图会「动」。
- 箭头 = 一条线 + 两条短线组成的箭头，不用 marker（rough 的抖动与 marker 对不齐）。

### 为什么不直接调用 Excalidraw

问过一次，结论是不值得，理由按重要性排：

1. **Excalidraw 内部就是 rough.js。** 「调用 Excalidraw」拿到的是同一个渲染器加一层很重的壳。我们真正想要的是它的**参数取值**，而参数直接设就行（见上）。
2. **中文是硬伤。** Excalidraw 的手写体（Excalifont / Virgil）**没有汉字**，中文会掉到普通字体。英文样本看不出这个问题，我们的图是中文的——用了它反而要再把霞鹜文楷塞回去。
3. **它是 GUI 应用，程序化生成很贵。** 要么手写 `.excalidraw` 场景 JSON（每个元素几十个字段，还带 `seed` 与 `versionNonce`），要么起 React 组件调 `exportToSvg`——都要 npm 和构建步骤，而现在整条链子是「一个 HTML 文件、零构建、零依赖」。
4. **它确实有一个真优势：产物能用鼠标改。** 但要给非工程的人微调时，**别指望 Excalidraw**——它只把外来 SVG 当一张图片贴进去，整块能挪、不能拆开改（官方原话：把 SVG 转成 Excalidraw 图元「至少目前不在本项目范围内」；能重新编辑的只有 Excalidraw 自己导出且勾了 embed scene 的图，场景 JSON 是压缩后塞进 SVG metadata 的，我们的图没有那段数据）。**正确做法是 `render_figs.py --svg` 出矢量，拖进 Figma / Illustrator / Inkscape 改**，那边会真的解析成可编辑路径与可编辑文字。两个前提：① 先在本机装上 `assets/fonts/` 里那两支字体（Architects Daughter、霞鹜文楷 Lite），这些工具通常不吃我们内联的 data-URI `@font-face`，缺字体就会替换掉；② rough.js 的手绘线是一堆细碎 path，那边能挪能改色，但改不出「这是个圆角矩形」——**结构性的改动仍然回配图页改代码再重出**。（真要在 Excalidraw 里拆开改，只有 Obsidian 的 Excalidraw 插件实现了 SVG 导入后 ungroup，属绕路方案。）

### 字体（方案 A · 已定）

| 用途 | 字体 | 来源 |
|---|---|---|
| 拉丁字母、数字、技术词 | **Architects Daughter** | `assets/fonts/ArchitectsDaughter-Regular.woff2`（28 KB，随库） |
| 中文 | **霞鹜文楷 Lite** | `assets/fonts/LXGWWenKaiLite-Regular.ttf`（13 MB，不进 Git，按 README 重下） |

- **技术名词一律保持英文原样**：MLP、Self-Attention、Weights、KV cache、SRAM、HBM、FLOPS 等，不译成中文再标英文。中文只承担说明。
- **字体必须子集化后内联**，不许指望读者本机有中文字体：

  ```bash
  python3 assets/fonts/subset_font.py --text-from "output/<标题>/<成品>.md" --out /tmp/wenkai.woff2 --css
  ```

  收全一篇成品的用字通常 200–300 KB，内联后 300–400 KB，完全可接受。
- 为什么不挂 CDN：Artifact 的 CSP **只允许 fonts.gstatic.com 提供字体文件**，自带字体只能走 data URI。

### 颜色

**语义色只有两种，其余都是版式色、不承担编码。** 跨图保持一致，读者认一次就够。**每种语义色都是"深描边 + 浅填充"一对**，浅填充是这套图不刺眼、久读不累的来源（借鉴 Akshay 的做法）：

**每种语义色是三档，不是两档：鲜艳的描边、很浅的填充、深的文字。** 这是「鲜艳又看得清」的关键——**用描边那支颜色去写字，一定不够黑**：`#E8590C` 写在 `#FFE3C7` 上只有 **2.9:1**，比浅灰还难读。

| 角色 | 描边 | 填充 | 文字 | 用在 |
|---|---|---|---|---|
| **计算受限**（语义） | `#E8590C` | `#FFE3C7` | `#A03C08` | MLP、权重、算力、吞吐、Tensor Core |
| **内存受限**（语义） | `#1971C2` | `#D3E9FA` | `#12558F` | Self-Attention、KV cache、带宽、容量、HBM |
| 中性部件 | `#6B6355` | `#EFE9D8` | `#1E1E1E` | 不属于上面两类的方框 |
| 纸底 | — | `#F7F2E4` | — | 整张图的底色，**暖黄纸，不是白** |
| 分组虚线 | `#8C8471` | — | — | 容器、边界、分隔线 |
| 图题与结论 | `#3B4FB8` | — | 图内大标题、底部结论句。**这支靛蓝紫只用在文字上，从不用来画框**，所以不会和「内存受限」的 `#1971C2` 混 |
| 解读句 | `#4A5BC4` | — | 结论下面那行小字，同一支靛蓝紫深一档（原来的 `#6C7FD8` 只有 3.3:1） |
| 注记 / 副标题 | `#6B6455` | — | 副标题、示意说明。**别用更浅的灰**，`#857F72` 只有 3.6:1，扫一眼就是「字太浅」 |
| 强调（少用） | `#C2255C` | `#FBD9E4` | 文字用 `#9B1B49`。全图题眼那一个东西 |

- **每个颜色上图前先算对比度**（相对纸底 `#F7F2E4`）。判据：**正文类文字 ≥ 4.5:1，纯图形元素 ≥ 3:1**。一段十行的脚本就能算，别靠眼睛估——本项目靠眼睛估的结果是六项里五项不达标（注记 3.6、解读句 3.3、虚线容器 2.1、橙字在橙底 2.9、蓝字在蓝底 4.0），用户扫一眼就说「字太浅」。
- **字号在手机上会缩到多小，是能算的**：`viewBox` 宽 1080 的图放进公众号，手机正文宽约 350pt，缩放比 0.32——**图上 13.5px 的标签到手机上只有 4.4pt**。所以小字下限是 11.5px，且**图上元素越少，手机上越读得清**；真读不动就该拆图或改竖版，不是把字再调小。
- **不许现编新颜色。** 概念套不进两类语义色，就用中性部件色。
- **底色用暖黄纸 `#F7F2E4`，不要白底。** 白底看久了刺眼，暖纸是这套风格最省事的一半。导出 PNG 时底色也要一起画进去（`render_figs.py` 读 `--paper`）。
- **默认 `opacity: 1`**，用颜色、字号、线宽做层次，不用透明度。
- 手绘风承诺浅色底，**不跟随深浅主题**，但背景与每个颜色都要显式画出来。

### 版面骨架（每张图都长这样 · 借鉴 Akshay）

图身上下各留一条固定的带，**四张图放在一起要像同一套东西**：

```
   ┌ 顶带 104px ─ 图题（26，#3B4FB8，半粗，居中）
   │              副标题（13，#857F72，居中，一句话说清这张图在看什么）
   ├ 图身 ──────  正常的图，坐标从 0 开始
   ├ 底带 122px ─ 一条横贯的虚线
   │              结论句（17，#3B4FB8，半粗，居中，一句话，句号收尾）
   └              解读句（13，#6C7FD8，居中，补一层「所以呢」）
```

- **图题必须画进图里，不要只写在网页的 `<h2>` 上。** 导出的 PNG 要能单独站住：公众号里一张图就是一屏，读者看不到网页上的标题。网页那边保留 `FIG. 0X` 这种小号眉标即可，避免和图内标题重复。
- **结论句是这张图的题眼**，不是图释的复述。图释（`<figcaption>`）说的是"这张图画了什么"，结论句说的是"所以你该记住什么"。
- **霞鹜文楷没有粗体，图题要靠描边补字重**：给 `<text>` 加 `stroke` 同色 + `stroke-width: 0.7` + `paint-order: stroke`。不补的话标题只靠字号和颜色撑，看着像正文。踩过：深藏青 `#2C3E7B` 的对比度其实有 8.8:1，"标题不突出"从来不是对比度问题，是字重与饱和度问题。
- 实现见 `output/Neil Movva - Making AI 10x Cheaper/图解 - 一个 Token 的芯片之旅.html` 里的 `ctx()` / `c.finish()`：图身画在一个 `translate(0, 104)` 的 `<g>` 里，坐标不用改，顶带底带各自画在根上。

### 尺寸与排版（借鉴 Agents365-ai）

- **中文标签算宽度要翻倍**：西文 `max(160, 字数 × 9)`，**CJK `max(160, 字数 × 18)`**。不翻倍就会截字——这是多数同类 skill 的通病。
- 字号层级：**图题 26 → 结论句 18 → 副标题 / 解读句 14** → 分组标签 14.5 → 正常标签 13.5 → 注记 12 → 小字 11.5。**11.5 是下限**，再小手机上就没法读了。
- 宽图放进 `overflow-x: auto` 容器并设 `min-width`，页面本身永不横向滚动。

## 四、图的文字部分

- **标题写「这张图在解释什么」**，不写它对应正文哪一节。❌「对应章节 · 公交车和私家车」 ✅「解码阶段为什么受内存带宽限制，批处理又改变了什么」。
- **每张图配一句「图释」**，说明它要说明的那个机制。图内只放短标签，解释性长句放图释。
- **标签的语域分三档，同一档内写法必须一致。** 图上语域不齐是最容易露怯的地方——同一张图里既有「算出 Q / K / V」又有「Self-Attention 打分」，一个是口语动词一个是半术语，读者立刻看出这不是行家画的。
  - **术语位**（方框标签、列头、轴标签）：用行业标准写法，同行拿去对得上。`QKV 投影` 不写「算出 Q/K/V」；`算术强度低` 不写「搬得多、算得少」；`Tensor Core 等待访存` 不写「Tensor Core 在等数据」。**这一档最不能松**，它决定这张图在专业读者眼里可不可信。
  - **说明位**（副标题、箭头标签、小注）：平实的解释句，**但动词要全套统一**。访存一律说「读取 / 写回 / 传输」，不要一会儿「搬」一会儿「读」。
  - **结论位**（底部两行）：写成可被引用的判断句，句号收尾。**去掉俏皮话**——「算力吃得饱」「用不着拼车」「又长一格」这类是编者自己的口语，没有出处也不精确。
  - **例外：嘉宾的比喻照留。** 它有出处（见 §一）。公交车 / 私家车留在副位并注明出自原片，不要为了「显得专业」把它删掉，那是原片的资产。
  - **判据**：专业读者看了不皱眉，外行看了不用查词典，就对了。**专业 ≠ 书面化**——「对 KV cache 做全量读取」并不比「读取整段 KV cache」更专业，只是更绕。
- **语言克制，去绝对化用词**。❌ 最低 / 最高 / 飞快 / 谁也没法兼得 / 任何单一芯片都只能接住一半　✅ 较低 / 较高 / 带宽高 / 容量与带宽此消彼长 / 单一芯片较难同时适配两端。技术用词按专业口径写。
- **原片里的比喻用画的，不用写的**：公交车、私家车这类形象概念直接画出车来，技术标签（`batch = N` / `batch = 1`）留在主位，比喻退到副标并注明出自原片。**比喻是嘉宾的，不是我们的。**
- **器件按其真实构造画**。晶圆级方案是「整片晶圆刻成一块芯片、内部按光罩分块、块间经切割道相连」，**不是圆里散落一堆小方块**（那是普通切割晶圆，恰好相反）；Blackwell / Blackwell Ultra 是**封装基板上并排两颗近光罩尺寸的 die、由 NV-HBI 相连，两侧共八堆 HBM3E**，**不是一颗中央裸片**（这条我们画错过一次，Exa 查证时才发现）。拿不准就先查证再画。
- **数字先核后画、出处不进图**（详见 §五）；示意性图形（阵列格数、分块数、堆叠层数）注明为示意、不按比例。

## 五、数字与专名的核对（硬约束）

> 用户 2026-09-03 当面立的规矩：**图要干净，逻辑要讲清楚，数字要准。口径和出处一律不进图。**

**1. 出处不进图。** 时间戳、页码、厂商文档名、`〔原片 26:06〕` 这类标注**一律不出现在图上**，全部集中到成品文末的「出处与边界」一节。图内只保留**非时间戳的归属说明**（例：`嘉宾说的 happy path`、`比喻出自原片`），因为「这是谁说的」本身就是图要表达的内容。

**2. 先核对，再上图。** 图上每个数字、每个技术专名，动笔前都要核到源头：

- **厂商规格以官方文档为准**（官方产品页、开发者文档、tuning guide），不照抄二手报道，也不照抄嘉宾的口头约数。
- **嘉宾口头说的数字是「陈述」，不是「规格」。** 两者不一致时**图上用官方值**，嘉宾的说法写进文末出处那一行、注明量级是否一致。（踩过的坑：嘉宾说 HBM「约 10 TB/s」、片上「约 500 MB SRAM」，官方是 B300 的 **8 TB/s** 与 L2 **126 MB**——量级对得上，具体值不对，直接上图就是错的。）
- **专名按官方写法**（大小写、连字符、代号），拿不准先查证；写法规则见 `skills/proper_noun_check.md`（CLAUDE.md Step 2.5 第 2 条）。
- **查证优先走 Exa MCP**（`mcp__exa__web_search_exa` / `mcp__exa__web_fetch_exa`），比通用 WebSearch 精准。检索时**描述理想页面而不是堆关键词**（「NVIDIA 官方讲 Blackwell Ultra 架构的技术博客里的规格表」好过「Blackwell 规格」），拿到 URL 再用 `web_fetch_exa` 读原文，不要停在搜索摘要上。**实测收益**：同一批数字，通用搜索只纠出「10 TB/s 应为 8 TB/s」，换 Exa 一次就翻出了**封装是双 die、由 NV-HBI 以 10 TB/s 相连**这个结构性事实——图上原来画成一颗 die，是错的。
- **没有公开口径的量不要编。** 例：NVIDIA 不公布片上 SRAM 的聚合带宽，那就只标容量，带宽用定性表述（「片上快得多」），不写一个看起来很像的数。
- **示意性图形**（阵列格数、堆叠层数、占用格子的填色）必须在图内注明为示意、不按比例。
- **画硬件之前先查封装拓扑。** 「一颗芯片＝一个方块」是直觉，不是事实：Blackwell / Blackwell Ultra 的一颗 GPU 是**两颗 die 经 NV-HBI 相连、对外呈现为单个 CUDA device**，画成一颗 die 就是错的。本项目已在这条上栽过两次（晶圆级方案画成普通切割晶圆；单 die 画成整颗 GPU），**器件形态和数量都算"数字"，同样要先核对再画**。

**3. 一一对应。** 图上出现的每个数字，文末出处区必须有一行对得上；交付前从图上倒着数一遍。

## 六、要画数据图表时

有数据要比大小、看趋势、看占比时，可以画 chart。**但仍然在这套系统里画**，用 rough.js 画柱、折线、散点（柱就是圆角矩形，折线就是 `linearPath`，都已经有现成 helper），沿用同一套纸底、语义色与版面骨架。**不要引第二套图表引擎**，一张图里出现两种字体两种配色，读者一眼就看出是拼的。

判据（借自 [lieflat-charts](https://github.com/larashero3-dotcom/lieflat-charts)，只借判据、**不安装**，原因见 §九）：

1. **先选图表类型，再动手。** 比大小用条形（横向条形比竖直柱更好放中文标签）、看时间趋势用折线、看构成用堆叠条形而不是饼图、看两个量的关系用散点。**不要默认柱状图。**
2. **一张图只用一套色系。** 分类多到语义色不够用时，用同一色相的深浅序列，别每根柱一个颜色。
3. **图元必须映射真实值。** 柱长、点位、刻度都要对应真实数字，不做装饰性图元、不截断 Y 轴起点。这就是本项目的忠实度红线在图表上的说法，和 §五 的核对规则是同一条。
4. **坐标轴与刻度要写单位**，示意性的图（如"相对成本"）必须在图内注明不是实测值。
5. **数据标注不得被曲线遮挡**（2026-09-23 用户口径）：数值标注一律配白底（或浅底）色块，放在点 / 线的空白一侧；起点、终点的标注放在红点正下方。位置一变线形可能又压上，所以不能只靠挪位置，必须配底色。
6. **图内不写口径批注或近似方法说明**：图内只留标题、轴、数据标注；方法与口径写进正文或图注。
7. **数据图优先取真实数据**：先找一手可查的数据（如成分股的实盘权重），再用历史价格回推；近似算法必须用正文里嘉宾说的数字自证量级。Yahoo Finance 的 chart 接口要带浏览器 `User-Agent` 才不被 429；「SPY 价格 × 股本」这类不成比例的近似不能当占比用。
8. **外部官方图不重画**：直接引用官方原图，加一行短图注（指标定义、日期、来源），见 `dialogue_transcript.md`「删减与去重原则」。

## 七、导出与嵌入正文

图是 rough.js 在浏览器里现画的，DOM 里才有形状、文件里只有一段脚本。要进公众号 / Notion / Blog，先落成静态文件：

```bash
python3 render_figs.py "output/<标题>/图解 - <名字>.html" --out "output/<标题>/figs" --scale 2
```

- 默认**只出 PNG**（2×，约 2200 px 宽），加 `--svg` 才额外出矢量。**成品目录 `figs/` 只放最终要进文章的图**，中间稿不要留——留了下一个接手的人分不清哪张是定稿。
- 正文里写 `![图 1 · <这张图在说什么>](figs/f1.png)`，**alt 要写全**：`notion_upload.py` 拿不到图时会退化成 `🖼️ [待补图片：<alt>]`，alt 是那句话的唯一来源。
- **一律加 `--no-open`，再用干净浏览器打开脚本打印出的地址。** 脚本默认调 `open` 走系统默认浏览器，而默认浏览器可能装着 **Midnight Lizard 这类调色 / 深色化扩展**——它会在导出前把整页重新着色，**浅填充全被染成饱和深色，而几何与对比度机检照样全绿**（扩展改的是最终着色，机检读的是坐标与色值属性，抓不到）。判据有两条：① `figs/` 里冒出不认识的 PNG（扩展往页面注了自己的 `<svg id>`，如 `midnight-lizard-filters.png`）；② 导出的图颜色比配图页里看到的深。本项目 2026-09-07 因此出过两张废图。干净浏览器可以用 Claude Code 内置的 Browser 面板、无扩展的 Chrome 独立 profile，或另一个不装扩展的浏览器。
- **图内文本不要用破折号 `——`。** 拉丁字体 Architects Daughter 没有中文破折号，会掉成两个连字符（`--`），而**机检不查字形、只查几何与对比度，一路全绿**。改用冒号或直接断句。
- **不要用截图**：掉字体、带浏览器缩放误差、每次尺寸都不一样。导出走的是按 `viewBox` 的精确栅格化。
- **不要为此引 Playwright / headless Chrome**：多 150 MB 依赖，换不来精度。

## 八、无障碍与自检

- `<figure>` 包 `<svg>`，配 `<figcaption>`；`svg` 加 `role="img"` 与 `aria-label`，label 把图说的那件事完整写一遍。
- **带文字的方框用实心浅填充，不要 hachure**：文字压在斜线网底上读不清。
- **先跑机检，再用眼睛看。** `render_figs.py` 导出时会自动做几何与对比度自检（`--no-lint` 可关），四类硬伤直接报出来：文字溢出画布、文字戳出所属方框、文字相互重叠、对比度低于 4.5:1（大字 3:1）。**有 ⚠ 就以非零码退出**，别把带告警的图放进 `figs/`。
  - 借自 [diagram-design](https://github.com/cathrynlavery/diagram-design) 的 ADR 0005：**「只活在散文里的规则，就是会发出坏图的规则」**。这条清单原来全靠肉眼，实测漏得很稳——机检第一次跑就在两张已经手工核过三遍的图上抓出 4 处真错。
  - **检查器自己必须带正反两极的用例**（这也是 ADR 0005 的原话：一个只报坏图、不验好图的检查器，调松阈值就能骗过自己）。跑 `python3 render_figs.py --selftest`：内置一坏一好两张图，坏图必须报出全部四类，好图必须零告警。**改了任何一条判据就重跑它。**
  - **实现注意（两个坑都踩过）**：① **不能用 `getBBox()`**——它不含祖先 `transform`，而图身画在 `translate(0,104)` 的 `<g>` 里，会把顶带标题和图身标签算成重叠，满屏假阳性；② **也不能直接用 `getBoundingClientRect()` 当画布**——SVG 没被 CSS 给尺寸时它返回 0×0，画布判据整个失效（对抗测试就是这么抓出来的：好图四条文字全被误报溢出）。**正解是用 `getScreenCTM().inverse()` 把屏幕坐标折算回 SVG 用户单位**，画布取 `viewBox`；这样既含全部 transform，又与代码里写的坐标同一套数，报错能直接对上源码。
- **机检只查「文字压文字」与「文字出框」，不查「文字压图形」。** 图里画了车、芯片、堆叠这类装饰或器件图形时，它压住旁边的文字自检照样全绿——本项目 2026-09-07 就是这样让小车盖住了两行结论句。**有图形元素的图，导出后必须逐格看一遍图形与文字的间距。**
- 交付前逐条过（机检管不了的部分）：① 渲染结果亲眼看过？② 每个数字核到官方出处、文末出处区有对应行？③ 图上没有时间戳与出处标注？④ 颜色只用了那两种语义色？⑤ 标题写的是「解释什么」？⑥ 页面本身不横向滚动？⑦ 有没有绝对化用词？⑧ `seed` 固定了吗？⑨ 底色是暖纸 `#F7F2E4` 而不是白？⑩ 图题、副标题、结论句、解读句四件都在图里？
